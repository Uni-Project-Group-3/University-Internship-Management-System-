# UIMS Firebase schema and readiness

This is the consolidated schema reference for the current source tree in this integration workspace. It describes paths and contracts used by code; it does not prove those paths exist in the target database. The canonical endpoint is `https://intership-managment-system-default-rtdb.europe-west1.firebasedatabase.app`, configured in `Web.config`. The configured project ID is `intership-managment-system`. Both are currently disabled for application traffic. `FirebaseApi.ashx` is the narrow authentication bridge for configuration, sign-in, refresh, identity, logout, and coordinator-only schema key inspection; it does not expose arbitrary database paths.

The adjacent `firebase-development-seed.json` is fictional and intended only for an isolated development database. It is not a production migration or safe root overwrite. Its four `TEST_UID_*` keys are placeholders. Create separate Firebase Authentication users in an isolated project and replace those profile keys with their issued UIDs before attempting login. No credentials are in the seed.

## Indexes

The proposed indexes are in `firebase-database-rules.proposed.json`: `users.studentId`; `assignments.studentId` and `assignments.academicSupervisorId`; placement student/profile/company/supervisor relationships; `opportunities.companyId` and `opportunities.status`; `tasks.placementId`; `taskExams.placementId`, `companyId`, and `createdBy`; and weekly report company/supervisor/student fields. Existing whole-root reads in application and other legacy pages need scoped query changes; indexes do not repair those authorization or data-minimization issues. Application indexes cannot be finalized until those pages use explicit scoped queries.

## Safety and mismatches

- All app modules that use `FirebaseDatabaseUrl` must use the single root in `Web.config`; Attendance adds its preserved `/uimsAttendance` prefix. Exams, tasks, boards, file metadata, weekly reports, placements, and final evaluation retain their existing top-level paths.
- Firebase Auth Web API key presence does not prove key/project match or provider enablement. `FirebaseAuthenticationEnabled=false`; Email/Password state cannot be checked offline.
- Server REST transports use ADC/Google credentials. Set the trusted deployment identity through protected host configuration, not frontend code or repository files. Admin privileges may bypass RTDB Rules, so server ownership checks are mandatory.
- `/weeklyReports` and `/fileAttachments` are empty in the seed because a report is not validly uploaded without an actual private Storage object. Upload a real `.docx` through the company workflow in an isolated bucket to exercise those paths.
- `OpportunityService` no longer contains seeded or process-local business records. The application and placement services are still incomplete: student apply, company decisions, and confirmed-placement creation are not yet one authenticated/idempotent Firebase workflow. This is a code blocker, not a JSON problem.
- Student opportunity status/major compatibility is implemented, but application/placement confirmation is still not atomic and the legacy page flows need scoped trusted service operations before production use.
- Attendance's localhost no-auth identity mode is disabled in code. Final Evaluation page compositions now fail closed unless a trusted factory is registered; the required Firebase-backed assignment, placement, approved-hours, task/report readiness adapters are not registered yet, so the official UI workflow remains unavailable.
- Firebase Rules are proposed as deny-by-default with query indexes. Do not publish them without reviewing how the trusted server identity accesses the services.

No live Firebase read/write, Storage operation, Authentication operation, import, or Rules deployment was performed.


## Application and confirmed placement lifecycle (implemented locally)

- `applications/{applicationId}`: `id`, `studentId` (university business ID), `studentUid` (Firebase Auth UID), `studentName`, `opportunityId`, `companyId`, `companyName`, `status`, `phone`, `cvLink`, `portfolioLink`, `motivation`, `reason`, `createdAt`; decisions add `decidedAt` and `companySupervisorId`; confirmation adds `placementId` and `confirmedAt`. Newly created IDs are deterministic `APP-` plus a SHA-256-derived key to make repeated submissions idempotent. Legacy IDs remain readable through indexed `studentId` queries; old records keyed by Auth UID are queried compatibly.
- `placements/{placementId}`: `id`, `applicationId`, `opportunityId`, `studentId`, `studentUid`, `companyId`, `companySupervisorId`, `academicSupervisorId`, `status`, `startDate`, `durationWeeks`, `requiredHours`, `createdAt`. The new ID is `PLC-{applicationId}`; no existing placement is rewritten.
- `placementClaims/{studentId}`: a conditional-write claim with `studentId`, `applicationId`, `placementId`, and `claimedAt`. It prevents confirming two accepted offers concurrently and lets an interrupted confirmation retry the same placement. This is a newly introduced node and must be included before enabling application writes.

Queries use `applications.studentId`, `applications.companyId`, `applications.opportunityId`, `placements.studentId`, and `users.studentId`; these indexes are included in `firebase-final-rules.json`. The claim is addressed by student ID and needs no query index. All operations resolve an active Firebase Auth UID and `/users/{uid}` profile on the server; application decisions require the linked company supervisor, and confirmation requires the owning student plus an assigned academic supervisor. Server ADC operations bypass RTDB Rules, so endpoint authorization remains mandatory.

Acceptance seat counts are updated with an ETag conditional write to `opportunities/{opportunityId}`. The application record is then conditionally updated. As with any multi-record RTDB workflow without a server transaction, interrupted writes require retry/reconciliation; live writes remain disabled pending emulator/live integration.
