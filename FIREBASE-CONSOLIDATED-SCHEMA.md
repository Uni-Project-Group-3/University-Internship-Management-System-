# UIMS consolidated Firebase readiness review

This is a source-code-derived integration inventory for the separate development copy. It is not a live-data inspection, migration, Firebase import, or claim that every page is currently backed by Firebase. The runtime Web.config remains disabled for Firebase, Authentication, Storage, and writes.

## Central target and configuration findings

The canonical Realtime Database URL is `https://intership-managment-system-default-rtdb.europe-west1.firebasedatabase.app`. `Web.config` now contains that exact value without a trailing slash. Its `FirebaseProjectId` is `intership-managment-system`, matching the project identifier supplied with the target database URL. All code references found for `FirebaseDatabaseUrl` read centralized application settings; the other matches are URL validation, not additional database roots. Attendance adds its established `/uimsAttendance` prefix to that shared root; final evaluations, Tasks, Exams, and weekly reports use the root directly.

The Web API key setting already has a value in Web.config, but this offline review cannot establish that it belongs to this project. The key is intentionally not copied into this document or the schema JSON. `FirebaseAuthenticationEnabled` is `false`; Firebase Auth Email/Password provider state cannot be verified without a Firebase console or authorized test. Login code uses the configured Web API key for sign-in, verifies the ID token with Firebase Admin, then reads `/users/{uid}`. The Admin SDK and trusted database/storage requests obtain credentials through Google Application Default Credentials; no credential availability or project binding has been verified here. `Firebase.Local.config` is referenced as an optional appSettings override but is absent from this copy. `FirebaseStorageBucket` is empty.

Firebase, authentication, Storage, weekly reports, attendance, Tasks, Exams, schema validation, and live-write switches remain disabled in Web.config. The target URL is configured only as an intended endpoint; no HTTP request was sent to it.

## Existing roots and proposed schema outline

The adjacent `firebase-development-schema.json` is a schema-reference catalog, not an RTDB import file. It lists observed paths without data records so it cannot fabricate users, task results, weekly reports, or evaluation history. Do not import it through Firebase Console; it is deliberately not a database-root export. Empty collection placeholders or invented records could erase or contaminate existing data if imported at the root.

No new schema nodes are proposed by this configuration review beyond the already implemented weekly report paths. The code expects the following deployed query indexes before corresponding scoped queries are enabled:

- `/users`: `studentId`.
- `/assignments`: `studentId`, `academicSupervisorId`.
- `/placements`: `studentId`, `studentProfileId`, `companyId`, `companySupervisorId`, `supervisorId`.
- `/weeklyReports`: `companyId`, `companySupervisorId`, `academicSupervisorId`, `studentId`.
- `/tasks`: `placementId`.
- `/taskExams`: `placementId`, `companyId`, `createdBy`.
- Existing applications should gain scoped query indexes for the fields actually used after their whole-root reads are replaced; current page code does not provide a reliable minimized query contract.

The current code’s query behavior is not uniformly efficient: TaskService and several legacy application pages read broad nodes or the whole database. Indexes alone do not fix those data-minimization and authorization issues.

## Security and integration requirements

1. Keep Realtime Database Rules and Storage Rules private. API keys identify a Firebase project for client Auth requests; they do not authorize database or Storage access.
2. Enable the intended Firebase Auth provider only after confirming the project and key match. Keep the existing verified UID → `/users/{uid}` contract and ensure each active account has a matching profile with supported role and business IDs.
3. Supply trusted server ADC/service identity using protected host configuration. Do not put a service-account JSON or privileged token in Web.config, JavaScript, or this repository. Because Admin/privileged server credentials can bypass Firebase Rules, retain server-side actor, ownership, and assignment checks and restrict who can invoke the server.
4. Validate least-privilege RTDB/Storage Rules and required indexes against the actual schema before enabling any service. The current offline code cannot prove Rules compatibility.
5. Before enabling, migrate the remaining Coordinator supervisor/group/placement pages, Academic progress monitor, ContactMessages and public contact-message write to authenticated or narrowly scoped trusted services. Register official final-evaluation adapters and supply an approved institutional policy. Keep module and live-write gates off until isolated end-to-end verification.
6. Only after authorized development integration tests pass should the owner set Firebase/auth/schema/write and Storage flags. None were enabled by this work.

## Readiness boundary

The user, profile, assignment, placement, opportunity, application, task, board, attachment, exam, report, attendance, and evaluation paths above are source contracts; they were not verified against live data. Several Coordinator/Academic/communication pages still use legacy direct REST or hard-coded identity logic, and Final Evaluation still needs its official page adapters, authorizer, approved policy, and connected progress sources. Those gaps cannot be fixed by a JSON import. Actual records, Rules, Auth provider/key pairing, ADC project identity/permissions, and the Storage bucket remain to be verified in an isolated Firebase environment.
